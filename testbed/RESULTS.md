execute, check result/flags/cycles against an independently computed expectation,

## Findings: 8 port bugs (+1 input-coverage follow-up in §9; all fixed)

### 1. `0x35` implemented as `AND zp,X`, but Python has no such instruction (CRITICAL)
* Python `SPL0X._execute[0x35]` = (`_dummy`, 1): illegal 1-byte instruction.
* C++ fetches 2 bytes and executes AND. First `0x35` in executed code desyncs PC by 1 byte **permanently**.
* Note `continue.md` already reports `PC diverges … (C++ executes 0x34 vs Python 0x20)` —
  `0x34` is likewise `_dummy` in Python, i.e. exactly the footprint of a 1-byte slip like this one.

### 2. `0x81` / `0xA1` (`STA`/`LDA (ind,X)`) fetch 3 bytes, Python uses 2 (CRITICAL)
* `SPL03.cpp` length table puts `0x81, 0xA1` with `0xBD` (3 bytes); Python lengths are 2.
* Effect: every executed `(ind,X)` consumes the next opcode byte as an operand byte —
  wrong zero-page pointer **and** PC off by one afterwards.

### 3. `CMP zp` / `CMP #` / `CPX #` N-flag formula is wrong (HIGH — likely the step-43,920 cause)
* C++ (`SPL03.cpp` ~L375-401): `nf_ = (a_ < value)`.
* Python (`SPL0X.py` `_cmp_*`): `NF = bit7((A - m) & 0xFF)`.
* Counter-examples proven by tests: `A=0x00 vs 0xFF` → result `0x01`, N must be **0**, C++ gives **1**;
  `A=0x80 vs 0x00` → result `0x80`, N must be **1**, C++ gives **0**.
  Any borrow with result `< 0x80` (or no-borrow with result `>= 0x80`, e.g. `0xFF-0x00`)
  flips N. Wrong N → wrong `BMI`/`BPL` branch → wrong control flow → wrong X →
  `LDA abs,X` reads a neighbouring byte — precisely the observed
  `A=0x6B` (Python, addr `0x046A`) vs `A=0x67` (C++) signature at `BD 56 04, X=0x14`.
* Fix: `nf_ = ((a - value) & 0x80) != 0`.

### 4. `ADC zp` / `ADC #` ignore decimal (BCD) mode (MEDIUM)
* Python `_adc` applies the `+6` / `+0x60` BCD adjust when `DF=1`; C++ `add8` is binary-only.
* Proven: `0x09+0x01 DF=1` → py `0x10`, cpp `0x0A`; `0x99+0x01 DF=1` → py `0x00/C=1`, cpp `0x9A/C=0`.
* Latent until the game sets `SED`; then values **and** carry diverge.

### 5. `BD LDA abs,X` page-cross cycle rule differs from Python (LOW for correctness, matters for trace parity)
* Python (`SPL0X.py` `_lda_abs_x`): `4 + ((PC_after_fetch ^ addr) > 255)`.
* C++ (`SPL03.cpp` ~L355-374): `+1 iff (base ^ addr)` crosses a page.
* Proven on the exact Apollo vector: `PC=0x06D5, base=0x0456, X=0x14, addr=0x046A` →
  py 5 cycles vs cpp 4. (Side note: the C++ rule is the hardware-correct 6502 rule;
  parity with the Python tracer still requires replicating Python's rule.)

### 6. `readMem` SFR hole falls through to ROM (MEDIUM)
* Python returns `0` for unmapped SFR (`0xC0–0xFF` not in `_io_tbl`, e.g. `0xC2`).
* C++ only special-cases `0xD0`/`0xD2`; `0xC2` returns the ROM byte (`0xAB` sentinel in tests).

### 7. `writeMem` ignores all SFR except `0xD0`/`0xD2` (MEDIUM)
* Python stores PortA/PortB latches, tone/noise/speech regs, bank select.
* C++ drops them: writing `0xAB` to PortA (`0xC1`) reads back `0x00` instead of `0xAB`.
  Any game using sound ports, `PortB`, or banking will diverge here.

### 8. (No bug found — explicitly verified as matching)
`LDX#`, `TXS`, `JSR`, `LDA#`, `STA zp`, `RTS`, `SEI`, `JMP`, `INC zp`, `BNE/BEQ/BCC/BCS`
(offsets, polarity, page-cross cycles), `AND#`, `AND zp`, `PHA/PLA`, `RTI`, `PHP`
(`PS=0xDF` all-flags packing), `STX/LDA/LDX zp`, `DEC zp`, `ORA zp/#`, `CLC`,
`ROL A` (carry in/out), `EOR#`, `STA zp,X`, `INX` — all parity-clean on every vector.

## Fixes applied (2026-09-23) — all verified, 0 gaps remaining

All 8 bugs were fixed in `portmaster-build/src/SPL03.cpp` (+ `include/brickemu/SPL03.hpp`
for the new SFR state). Testbed mirrors were updated to the fixed logic.

| Bug | Fix |
|---|---|
| `0x35` as AND | Removed from length table and handler switch → 1-byte illegal instruction, like Python `_dummy` |
| `0x81`/`0xA1` 3-byte fetch | Moved to the 2-byte group; handlers unchanged (operand is now the single zp byte) |
| `CMP`/`CPX` N flag | `nf_ = bit7(a - value)` instead of `(a < value)` |
| `ADC` binary-only | New `SPL03::adc()` replicating `SPL0X._adc` incl. BCD `+6`/`+0x60` adjust when `DF=1` |
| `BD` cycles | `4 + ((pc_after_fetch ^ addr) > 255)`, i.e. Python's `PC^addr` rule |
| SFR read hole | Full SFR map (`C0/C1/C3/C4/C6/CC/CE/D0/D2/D4/D5/D7`); unmapped SFR → 0; `D5` reads `(cycles>>3)&1` |
| SFR write gap | Latches/regs stored (`C0` via `setIoCtrl` with PDIR/prescalar/ROSC parity, `D5 &= 0xBE`, `D7 &= 0x1` per `SPL03.py` overrides) |
| Trace noise | Removed per-step `cerr` debug (`debug_count`, `BD debug`, `SNAPSHOT`/`RESET` prints) |
| Bonus parity fix | `clock()` now replicates Python's ROSC/CPU-stop gating (timers-only when stopped) |

Verification after fix:
* `./testbed/run_tests.sh` → Python **189/189 pass, 0 mismatches**; C++ **182 parity pass, 0 gaps, 0 harness failures** (41 opcodes after §9 below); DisplayBuffer tests all pass.
* Apollo 18 trace comparison (Python `cores.SPL03` vs `brickemu --trace`): **5k / 50k / 200k steps, 0 mismatches** (was: 11 mismatches at ~43,920). Cycle counters match exactly (50k: 194610 = 194610).

## 9. Follow-up find (input-driven coverage): missing ROR zp / ROR A — FIXED
The no-input trace was insufficient: pressing StartP drives the game into code
using `66 ROR zp` (45,862× in a 700k-clock input session) and `6A ROR A`,
neither ported. C++ spun forever on the 1-byte illegal fallback at `0x8BD`
(ROR-based wait loop whose exit needs the rotated carry), diverging completely
(`start+200k`: C++ `pc=0749` vs Python `pc=08B3`, VRAM and cycle counts apart).
Input-driven Python coverage over boot + On/Start + D-pad mashing showed 38
distinct opcodes; the only executed-but-unported ones were `0x66`/`0x6A`
(Python `_ror_zp`/`_ror_a`, incl. the quirky `N = incoming carry` and
`Z = ((prev & 0xFE) | Cin) == 0` semantics, replicated verbatim).
After porting both (+ unit tests in both languages):
`boot → OnOff → StartP` checkpoints match **bit-for-bit incl. `ictr`, `cyc`
and VRAM digest** (`start+200k: pc=08B3 A=C3 X=2F …, ictr=450691 cyc=1931169`,
VRAM 4 bits lit, both sides; no illegal-instruction output).

## Suggested fix order
1. Length table: `0x81`/`0xA1` → 2 bytes; `0x35` → illegal 1-byte `_dummy` (or a deliberate,
   documented extension — but then Python parity is abandoned by choice).
2. `CMP`/`CPX` N flag → bit 7 of the subtraction result.
3. `readMem`/`writeMem` SFR coverage (hole → 0; all `_io_tbl` writes).
4. `ADC` BCD adjust when `DF=1`.
5. `BD` cycles → Python's `PC^addr` rule for trace parity.
6. Re-run `./testbed/run_tests.sh` (expect 0 gaps) then the 50k/200k trace comparison
   from `continue.md`.
## 10. New-game crash `0x5D at 0x27B`: missing LDA zp,X — FIXED
Symptom was misleading: Python maps `0x5D` to 1-byte `_dummy` (illegal), and
pure-Python execution of the selection path never fetches it — the crash was
PC desync, not a bad opcode. Coverage of the real path (on → start → browse
5 games → choose → launch → gameplay) showed `B5 LDA zp,X` executed 1,993×
with no C++ case: C++ consumed 1 byte instead of 2, slipped, then fetched
data byte `0x5D` as an opcode at `0x27B`. Fix: `B5` handler (2 bytes,
4 cycles) + unit tests both sides. Proof: 14,260-checkpoint lockstep
C++-vs-Python over the whole selection path — **identical, zero illegal
output**. Final suites: Python **211/211**, C++ **204 parity, 0 gaps**.

## 11. Terminal frame parity + the instructions-vs-cycles trap — VERIFIED

17 scripted frames (`on,start`, 0–160) rendered through the C++ terminal
frontend are now **bit-identical** to Python renders from cycle-matched
states. Along the way this caught a methodology bug worth recording: one
`clock()` call = one *instruction* (2–7 *cycles*), so "23000 clock() calls"
(Python test scripts) is ~4× more emulation than "23000 cycles" (frontend
frame budget at 690 kHz / 30 fps). Comparing those two framings shows
different animation/multiplex phases that look like real divergences but
aren't. All frame comparisons now use cycle targets on both sides
(`tools/eval_report.py` fixed the same way). Rule: exact-count lockstep for
the core, cycle-matched states for frames.

## 12. Held-key auto-repeat, single-char cells, HUD decode — DONE

*Held keys*: terminal input has no key-up events; the old code stacked one
release per auto-repeat char, opening periodic gaps (racing-game steering
died mid-turn). `HeldKeys` now refreshes the release deadline on every
repeat — a held key stays continuously driven until `--hold-ms` (default
200) elapses with no repeat. Unit-tested (`test_term_input.cpp`).
*Cells*: `--pf` renders single `'x'` / `' '` per playfield cell.
*HUD*: non-playfield bits mapped (table below), 7-seg decoded
(`Apollo18Hud.hpp`, unit-tested, live cross-checked C++ vs Python:
`SCORE  0000 SPEED 1 LEVEL 1 SOUND ON` identical). `--pf` appends the
`SCORE … SPEED … LEVEL … SOUND …` footer; interactive shows it live.
